Guava, explained through our demo

Guava runs the live voice conversation. Our Python code gives it a job, collects structured answers, and decides what happens next.

Our demo, Second Draft, helps someone rehearse a difficult conversation: describe it, practice with a fictional counterpart, get feedback, and try once more.

Based on the current local main.py and official Guava docs. Checked August 29, 2026. Installed SDK: 0.40.1. This page is a teaching simulation, not a connected voice agent.

01Two systems cooperate during a call

Think of Guava as the person performing the conversation and our code as the director. The director chooses the scene and the goal; the performer handles each spoken turn.

“Expert” means our application code. It does not have to be a second AI model. This demo uses Python handlers, strings, and ordinary conditionals. Guava’s cloud service provides the conversation intelligence.

Guava can contact an Expert running on a laptop through its outbound connection; development does not require a public web server. “Local audio” still uses Guava’s cloud. Architecture reference.

What Guava supplies

Speech recognition (STT), conversational response generation, speech synthesis (TTS), and the connection between the caller and our logic.

What makes this our product

The rehearsal workflow, fictional-persona instructions, collected fields, coaching goals, do-over decision, and exit behavior.

create_agent() creates one guava.Agent when the runtime starts. Mira and Alex are two personas used by that agent within the same call, not two separately deployed agents.

02The six building blocks to learn

Building blockPlain meaningOur demo
AgentThe configured assistant and its registered handlers.Second Draft, initially named Mira.
CallOne conversation session. Use it to read answers and send instructions.The same call survives coach → roleplay → coach.
PersonaWho the assistant is playing and which voice it uses.Mira / grace, Alex / jack.
TaskThe current goal, checklist, and completion guidance.intake, rehearsal, debrief…
FieldA structured answer collected through conversation.difficulty = "realistic".
CallbackA Python function invoked when an event happens.When intake completes, switch into roleplay.

The important distinction: a persona describes who to be; a task describes what to accomplish now. Our code changes both at role transitions. Guava supports changing name, purpose, organization, and voice with set_persona(). Persona reference.

A checklist has three kinds of item

  • guava.Say("..."): an exact statement to speak, such as the opening disclaimer.
  • guava.Field(...): an answer to collect, such as the caller’s desired outcome.
  • A regular string: an instruction, such as “Offer one concrete improvement.” Guava chooses the wording.

The checklist structures the conversation without scripting every response. Task reference.

Guava collects revised_line and is instructed to respond once. When this task completes, Python goes directly to takeaway.

def on_do_over_complete(call: guava.Call) -> None:
    if _transition(call, Stage.DO_OVER, Stage.TAKEAWAY):
        _start_takeaway(call, after_do_over=True)

This walkthrough follows normal completion. Pausing during a do-over can return to debrief, where retry can be offered again: there is no global retry counter. The one-response limit inside the task also relies on model guidance.

Once Guava reports the takeaway task complete, the registered handler verifies the stage, marks it ended, and asks Guava to wrap up and hang up.

6. Close the call

Persona
Mira, coach
Action

In the installed SDK, hangup() queues a natural-language wrap-up instruction. It does not synchronously disconnect the call at that Python line.

Our _close() helper first sets the application stage to ended to suppress duplicate actions. The separate on_session_end callback logs the termination reason when the session actually ends. Application state, a queued hangup instruction, and an ended call are different things.

Alternate route: leave the rehearsal

Persona
Mira, coach · voice grace
Task
safety_exit
Entered by
on_caller_speech(call, event) after a phrase match

Python normalizes the transcribed utterance and checks it against a fixed list of explicit crisis phrases. A match changes the application stage to safety_exit, restores Mira, and assigns the exit task. An escalation event can also enter this route.

call.set_variable(STAGE_KEY, Stage.SAFETY_EXIT.value)
_set_coach_persona(call)
call.set_task("safety_exit", ...)

The task tells Guava to stop roleplay and give human-support information. It then stays available for resource clarification without returning to roleplay; it does not automatically hang up. This implementation does not place an emergency call or transfer the caller.

The phrase check is a narrow backstop, not a clinical assessment. It can miss paraphrases and speech-recognition errors, or match quoted and negated statements. This simulator only illustrates the intended route.

04Read the Python as events and reactions

You do not need to follow every line. Start in create_agent(): it registers the functions that react to events. Guava also supports decorator syntax, but our current code registers handlers explicitly.

# Registration inside create_agent().
agent.on_call_start(on_call_start)
agent.on_caller_speech(on_caller_speech)
agent.on_task_complete("intake")(on_intake_complete)

# A complete guarded transition from our code.
def on_rehearsal_complete(call: guava.Call) -> None:
    if not _transition(call, Stage.REHEARSAL, Stage.DEBRIEF):
        return
    _start_debrief(call)
  1. Register: on_task_complete("intake") connects that task ID to the intake-completion function.
  2. Receive: Guava reports that the task completed and the SDK invokes the function with the current Call.
  3. React: Python checks the expected stage and any required fields, then queues a persona change and the next task.
  4. Continue: Guava conducts that stage. The Python function does not sit waiting for each spoken answer.

That loop is the architecture of our app: event → Python decision → command → conversation → next event. Stage names the allowed stages; _transition() rejects callbacks that do not match the expected current stage. In SDK 0.40.1, task and persona methods queue SetTaskCommand and SetPersona objects.

Why use several tasks?

“Collect the scenario” and “act like a colleague” are different jobs. Assigning a focused task at each stage makes our intended sequence readable and gives Python explicit points to branch. It does not make the model’s behavior inside a task fully deterministic.

05Spoken answers become usable state

Fields come from the caller

scenario, relationship, desired_outcome, difficulty, roleplay_consent, next_step, revised_line, and takeaway.

For example, Guava collects a choice from “gentle”, “realistic”, or “challenging”; our code reads it with call.get_field("difficulty").

Variables track application state

Our code writes the second_draft_stage variable through STAGE_KEY. Its values include intake, rehearsal, safety_exit, and ended.

The caller does not supply the stage. Python uses it to decide which transitions are valid and reject late or duplicate callbacks.

Guava’s Field API describes how to collect and validate an answer. A field’s question guides phrasing; use Say when exact wording is required. Field reference.

These are values associated with the call, not proof of durable product memory. Our application has no database, RAG knowledge base, CRM integration, or cross-session learning code. It does not train a model during the rehearsal.

What sensitive=True actually means

We flag the scenario, desired outcome, revised line, and takeaway. Guava documents best-effort redaction of sensitive values from stored transcripts and recordings. It explicitly warns that this flag does not guarantee exclusion from diagnostic or debug data. Sensitive-field documentation.

Our code also disables SDK telemetry before importing Guava and packages scenario values as bounded JSON labelled as untrusted data. These measures do not establish cloud retention policy or perfect prompt-injection resistance. Values still enter the roleplay purpose. Use fictional details and do not promise that nothing is stored.

Stage checks reject ordinary task-completion callbacks after a safety exit. The exit remains active for resource clarification; it does not resume rehearsal. An explicit end request can still close the call. These are application rules, not proof that the live service responds instantly.

A useful rehearsal before presenting

  1. Use the fictional Friday-work scenario. Check that the setup is understood.
  2. Listen for the switch from Mira to Alex. Say “coach” and check the actual response.
  3. Ask for one do-over, give a revised line, and confirm it reaches the takeaway and ends.
  4. Repeat using the finish path. Verify the intended presentation channel separately, especially the real phone path.

08Explain the tech in 30 seconds

“Second Draft lets you rehearse a difficult conversation by voice. Guava handles listening and speaking. Our Python Expert runs a sequence of tasks: collect the setup, switch into a fictional counterpart, return as a coach, and offer one do-over. We change the persona and voice inside the same call, and use structured fields and callbacks to decide what happens next.”
“Is this just a prompt?”

There are prompts inside it, but also a guarded stage machine, structured answers, a consent gate, persona changes, retry/finish branching, and pause/end/exit handlers. The model still decides much of the turn-by-turn behavior.

“Where is the AI model?”

Guava’s hosted Dialog System generates the conversation. Our code does not choose or host a separate language model, and the exact underlying model is not identified by this repository.

“What would you improve next?”

First prove the complete live call. Then, if strict limits matter, add turn counting and a retry budget that also covers pauses. Test pause-phrase variants, actual voice switching, and keypad configuration. These are possible follow-ups, not changes made by this guide.

09Check whether it clicked

Answer each question out loud before opening it.

1. Who writes Alex’s next spoken sentence?

Guava’s Dialog System generates it using the active persona, task, and conversation context. Our Python code supplies the setup and instructions, not each sentence.

2. What is the difference between a field and a variable here?

A field captures a caller answer, such as next_step. A variable records program state, such as second_draft_stage. Neither is a database in this application.

3. If 19 offline tests pass, have we proved “coach” pauses a phone call?

No. The tests prove routing when a speech event with matching text reaches our code. They do not verify microphone capture, transcription, delivery of the event, or the live agent’s response timing.

4. Does the switch to Alex start a new agent or a new call?

Neither. set_persona() changes identity, purpose, and voice on the current call. set_task() changes its current job.

5. Where would a future database save belong?

A task-completion handler gives a clear point to act on collected fields, for example after the takeaway. But saving rehearsal content would require deliberate consent, access, and retention design. It is not present now.

If you can explain persona → task → field → callback using the Friday-work example, you understand the core of our Guava demo.
